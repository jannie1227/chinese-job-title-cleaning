# 职位匹配前的四变量清洗

当前采用 v1.2.12 常规清洗交付版。四项核心元数据为招聘岗位、招聘类别、初级分类和上市公司行业。职位描述不进入这条清洗及其职业证据判断。

## 方法

1. 保留原字段，在新字段中记录清洗值及操作。
2. 处理有依据的公司、地名、招聘宣传、待遇和岗位编码包装，保护技术、材料、产品及实际职能限定。
3. 分别解析招聘类别和初级分类，区分职业提示、平台行业、就业类型及招聘渠道。
4. 将分类证据与职业核心比较，并记录其用途：辅助证据、仅扩展候选、冲突禁用或待复核。
5. 保留多职业子候选；对信息不足或没有职业核心的记录设置分流状态。
6. 输出主表、去重匹配任务字典及记录桥接表，核对主键、行数、年度数和频数总和。

不全局删除括号、数字或必要技术符号。未知实体和缩写保持保守处理；来源平台行业不替换上市公司行业。

## 交付契约

| 产物 | 规模 | 用途 |
| --- | --- | --- |
| 清洗主表 | 4,073,781 行，37 列 | 原记录与清洗、匹配分流字段 |
| SOC 匹配任务字典 | 2,112,545 行，25 列 | 去重后的职业候选匹配任务 |
| record_id 桥接表 | 4,073,781 行，9 列 | 原记录到任务字典的连接 |

`soc_input_route` 分为 `CANDIDATE_READY`、`REVIEW_REQUIRED`、`MULTI_OCCUPATION`、`NO_OCCUPATION`。第一类允许准备候选，其余按各自条件处理。每条原记录继续保留。

`occupation_hint_auxiliary` 仅在允许辅助使用时提供职业提示；`occupation_hint_candidates_only` 仅用于扩展候选。冲突或格式损伤来源不能绕过禁用状态成为职业判断依据。

`final_match_item_id` 的键同时涵盖清洗元数据、语义路线、允许使用的证据和未决标记。不能仅按职位名称重建它，也不能用文本或行号替代 `record_id` 连接。

## 复现状态

实际源码中的 `ruleset_version` 为 `routine_v1.6_standard_v1.2.12_dev`，交付状态由另行封存的交付文件记录。原交付的 `ruleset_hash` 为 `7681e28ef3ba3f5400fdd6983acac3061561c19d32c2f3a8f4d2fe01f9e87632`，涵盖封存输入、固定规则、开发锁、未决组合和交付脚本。

公开入口 `job-title-revise` 从 v1.2.11 封存格式的 31 列表开始，包含最后一层修订实际调用的九个规则模块。完整列名和顺序见人工示例；输入可为 CSV 或 CSV.gz，ID 和空值按字符串保留。输出目录必须尚不存在，重复 ID 或工程约束失败时不发布结果。

公开输出主表仍为 37 列、字典为 25 列；桥接表为 `record_id,final_match_item_id,soc_input_route,ruleset_version,ruleset_hash` 五列。旧研究桥接中的历史 ID 不由公开入口重建。公开入口的 `ruleset_hash` 根据入口代码、九个冻结模块和本地待讨论配置计算，不冒用上面记录的私有交付哈希。

原研究封存输入的 SHA-256 为 `a6edbed01982b14658d98da8c23684a2ba09c878b11d258652e1253d38dc16a3`。处理该输入必须提供 `--pending-rules` 指向对应的本地待讨论组合表；该表包含 27 个原始四字段组合，未随仓库公开。其他符合输入契约的表可以不提供该配置，但不能据此声称具有原研究的完整未决标记。

待讨论配置为 JSON 对象：键是依次包含原始岗位、招聘类别、初级分类、上市公司行业的紧凑 JSON 字符串，值为 `AI_KNOWN_UNRESOLVED`。键的编码必须与 `json.dumps(fields, ensure_ascii=False, separators=(',', ':'))` 一致。本地配置的文件哈希写入运行清单，原文组合不会写入公开源码。

该入口不包含原始数据至 v1.2.11 的上游清洗、私有企业证据和历史字典依赖。准确的复现范围为“封存 v1.2.11 → v1.2.12 末轮修订与分流”。
